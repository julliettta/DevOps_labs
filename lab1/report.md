# Отчёт по Лабе 1 — nginx

## С чего всё началось

Задача лабы — поставить nginx перед нашим сервисом из Лабы 0 так, чтобы 
он не просто "раздавал страницу", а реально работал как боевой прокси: 
с HTTPS, с несколькими копиями бэкенда, с защитой некоторых путей и с 
отказоустойчивостью. То есть нужно было собрать небольшую копию того, 
как выглядит инфраструктура настоящего сайта.

Сразу было понятно, что самое интересное и самое страшное в этой лабе — 
пункт про "погасите один бэкенд и покажите, что сайт жив". Именно ради 
этого всё остальное (upstream, балансировка) и делалось.

## Что делали по шагам

Начали с создания отдельной ветки `lab1-nginx` в git — чтобы не 
трогать main, как и договаривались с самого начала курса. Внутри 
создали структуру папок: отдельно бэкенд, отдельно фронтенд, отдельно 
всё, что касается конфигурации nginx (сертификаты, конфиги, страницы 
ошибок).

### Дорабатываем бэкенд из Лабы 0

Взяли готовый Flask-бэкенд с заметками и добавили ему одну важную вещь — 
переменную `INSTANCE_ID`. Смысл в том, что мы будем запускать две 
копии одного и того же приложения на разных портах (5001 и 5002), и 
нужно было как-то визуально отличать, какая из копий ответила на 
конкретный запрos. Решили просто добавлять ID инстанса прямо в JSON-ответ 
и в заголовок — это потом помогло наглядно показать балансировку.

### Самоподписанный сертификат

Тут словили первую неожиданность: команда openssl ругалась на формат 
subject name, хотя выглядела правильно. Оказалось, Git Bash на Windows 
сам переделывает пути, начинающиеся с `/`, в Windows-путь — то есть 
`/CN=lab1.local` превращался в какую-то дичь типа `C:/Program 
Files/Git/CN=lab1.local`. Решилось легко — поставили двойной слэш 
(`//CN=...`), и всё заработало. Мелочь, но минут 20 на это ушло, было 
немного обидно спотыкаться на ровном месте.

Чтобы у нас было не просто "localhost", а красивые домены `lab1.local`

### Собираем главный конфиг nginx

Это был самый долгий этап. В одном файле `nginx.conf` 
нужно было уместить вообще всё: редирект с http на https, два 
виртуальных хоста, проксирование `/api` с балансировкой, alias для 
`/docs`, лимит запросов и авторизацию для `/admin`. Писали по частям, 
проверяя после каждого добавленного блока, что nginx вообще стартует 
(`docker logs`), потому что одна опечатка — и контейнер падает сразу 
при запуске.

### Запускаем nginx в Docker

Здесь тоже не обошлось без сюрприза: nginx внутри контейнера не мог 
достучаться до бэкендов, которые крутятся на компьютере снаружи 
контейнера. Разобрались — нужен специальный флаг 
`--add-host=host.docker.internal:host-gateway`, который говорит 
контейнеру, как найти "хозяина". После этого всё заработало с первого 
раза.

## Проверяем каждый пункт задания

Дальше пошла самая приятная часть — проверка, что всё реально работает, 
а не просто "выглядит правильно".

### HTTP редиректит на HTTPS

```bash
curl -I http://lab1.local
```
Получили `301` и ссылку на https-версию — ровно то, что нужно.

📸 `screenshots/07-http-redirect.png`

### Балансировка между двумя бэкендами

Сделали несколько запросов подряд на `/api/notes` и увидели, как в ответе 
чередуются `backend-1` и `backend-2`. 

📸 `screenshots/08-load-balancing.png`

### Главный момент — убиваем один бэкенд

Вот ради этого всё и затевалось. Остановили `backend-2` (просто Ctrl+C в 
терминале) и снова начали стучаться в `/api/notes`. Сайт продолжил 
отвечать `200`, просто теперь все ответы шли от `backend-1`. Это было 
самое наглядное доказательство того, что мы поняли смысл лабы — сервис 
действительно пережил "падение" половины бэкенда, и пользователь этого 
даже не заметил бы.

📸 `screenshots/09-failover.png`

### /admin закрыт паролем

```bash
curl -k -I https://lab1.local/admin/        # 401 без пароля
curl -k -I -u admin:admin123 https://lab1.local/admin/   # 200 с паролем
```
Сработало сразу, без сюрпризов.

📸 `screenshots/10-admin-auth.png`

### Лимит запросов — тут было интереснее всего

Сначала пробовали флудить `/api` обычным циклом `for` с curl — и ничего 
не происходило, все ответы были `200`, хотя мы отправили уже чуть ли не 
сотню запросов. Начали разбираться — оказалось, что `curl` в цикле 
запускается слишком медленно, между запросами проходит больше времени, 
чем наш лимит (5 запросов в секунду) успевает "заметить". Решение — 
слать запросы параллельно через `xargs -P`. И тут вместо ожидаемого `429` 
полезли коды `503`. Снова пришлось разбираться — выяснилось, что по 
умолчанию nginx при превышении лимита отдаёт именно `503`, а `429` нужно 
включать отдельной директивой `limit_req_status 429`. Добавили её — и 
всё сразу стало работать как надо.

Было забавно, что "ограничение частоты запросов" звучало как самый 
простой пункт в задании, а на деле заняло больше всего времени и 
экспериментов.

📸 `screenshots/11-rate-limit.png`

## Что в итоге

В целом лаба оказалась куда объёмнее, чем казалось по описанию — почти 
каждый пункт на практике давал маленький сюрприз (то Git Bash ломает 
пути, то Docker не видит хост, то nginx отдаёт не тот код ошибки). Но 
именно разбор этих мелких проблем и дал понимание, как это всё реально 
работает под капотом, а не просто "скопировали конфиг и запустили".

Самое ценное — увидеть собственными глазами момент отказоустойчивости: 
выключаешь один из двух серверов, а сайт даже не моргнул. Ради этого 
ощущения, кажется, и задумана вся лаба.
